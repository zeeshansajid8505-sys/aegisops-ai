# ADR-018: AI-Assisted Root Cause Analysis, FastAPI Inference Integration, Topology-Aware Incident Reasoning, and Human-Approved Remediation Runbooks

## Status
Accepted

## Context
Across Phases 0 through 6, AegisOps AI established a comprehensive observability foundation:
- Multi-tenant organizations, memberships, and role-based access control (RBAC).
- Service catalog with synchronous/asynchronous dependency directed acyclic graphs (DAG) and cycle detection.
- Active synthetic health probes with strict Server-Side Request Forgery (SSRF) validation.
- Streaming OpenTelemetry (OTLP) metric ingestion with strict cardinality protection and sliding-window alert evaluation.
- Multi-alert incident correlation with monotonic severity escalation and timeline audit trails.
- Real-time operations cockpit with WebSocket event dispatching and refined, accessible UI/UX.

In production incidents, on-call SREs face intense cognitive load:
1. High alert volumes during cascading service outages obscure the primary point of failure.
2. Relying on generic conversational chatbots produces ungrounded hallucinations, lacks multi-tenant isolation, and creates security risks through unauthorized mutations.
3. Complex microservice topologies make manual graph tracing across upstream and downstream dependencies slow and error-prone.
4. Autonomous AI remediation without human sign-off poses catastrophic operational risk in enterprise infrastructure.

## Decision

### 1. Strict Knowledge Separation Architecture
AegisOps AI strictly separates incident reasoning into three immutable epistemological categories:
- **Observed Fact**: Deterministic, bounded telemetry evidence retrieved from the database within a lookback window `[detectedAt - 30m, detectedAt + 10m]`. Includes health probe failures, firing alert episodes, metric anomalies (>2.0 standard deviations from baseline), and responder notes.
- **AI Hypothesis**: Ranked root cause candidates generated by the Python FastAPI reasoning engine (`RcaEngine`), parameterized by topological distance, temporal alert precedence, and negative counter-evidence penalization. Hypotheses are explicitly marked `PROPOSED` and carry confidence bands (`HIGH`, `MEDIUM`, `LOW`) and machine reason codes.
- **Human-Confirmed Root Cause**: AI hypotheses NEVER mutate incident root-cause truth automatically. An authorized operator (`ai.analysis.feedback` permission) must review evidence and explicitly click "Confirm Root Cause" with operational notes, or "Reject" with audit reasoning.

### 2. Multi-Factor Topological & Counter-Evidence Reasoning Engine
The FastAPI inference service (`apps/ai-service`) implements a deterministic, multi-factor scoring model:
- **Graph Topology Embedding (`TopologyEmbedder`)**:
  - Computes 16-dimensional spectral / truncated SVD embeddings over normalized graph adjacency matrices.
  - Generates deterministic SHA-256 graph fingerprints for cache invalidation and change detection.
  - Evaluates direct upstream dependencies, giving higher initial probability to upstream providers over downstream consumers.
- **Temporal Precedence & Metric Anomaly Evaluation**:
  - Boosts scores for services with the earliest firing alerts in the correlation cluster (`EARLIEST_ALERT_FIRING` +35 pts).
  - Evaluates metric standard deviation spikes (`METRIC_ANOMALY` +25 pts) and critical synthetic probe failures (`CRITICAL_PROBE_FAILED` +30 pts).
- **Negative Counter-Evidence Penalization (`HEALTHY_COUNTER_EVIDENCE`)**:
  - Actively checks candidate services in the topology for passing health probes and normal telemetry baselines.
  - Deducts up to -60 points (`score = max(0.0, score - 60.0)`) and records counter-evidence references (e.g. `service:<id>:probes_healthy`).
  - Completely prevents healthy upstream dependencies from falsely ranking as root-cause culprits.

### 3. Strict Multi-Tenant Security & Network Boundary
- The browser frontend (`apps/web`) communicates exclusively with the NestJS Core API (`http://localhost:3001`).
- The FastAPI AI inference service (`http://localhost:8000`) is an internal backend service. All endpoints (`POST /v1/rca/analyze`) require an internal pre-shared key passed via the `X-Internal-Service-Key` header (`AI_INTERNAL_API_KEY`).
- Unauthenticated or client-side calls to `/v1/rca/analyze` return `401 Unauthorized`.
- NestJS enforces tenant boundary isolation on all RCA endpoints (`SessionAuthGuard`, `OrganizationMemberGuard`, `@RequirePermission`).

### 4. Human-Approved Remediation Runbooks (Zero Autonomous Shell Execution)
- Remediation runbooks are structured, human-executed operational checklists.
- **Zero Autonomous Mutations**: The system never executes arbitrary shell commands, runs container restarts, or mutates cloud infrastructure directly.
- Runbooks are authored as templates under `Settings → Runbooks` tab (`runbooks.manage` permission) and linked to services or incident severities.
- During an incident, operators start execution (`runbooks.execute`), step through ordered instructions, record verification notes, and check off steps manually.
- Every step completion records timestamped audit records (`IncidentTimelineEvent`) linked to the operator's membership.

### 5. Seamless Integrated Operations UI (No Chatbot Modals)
- Completely avoided generic conversational interfaces (no floating chat bubbles, typewriter text effects, or open-ended prompts).
- Integrated the `IncidentAiRcaPanel` directly into the existing `/incidents/[incidentId]` incident command page.
- Visual elements:
  - Bounded observed facts table with source entity links.
  - Ranked hypothesis cards with evidence/counter-evidence breakdown and topological distance badges.
  - One-click "Confirm Root Cause" modal with summary input.
  - "Reject Hypothesis" modal with mandatory audit trail explanation.
  - Active Runbook Checklist runner displaying real-time progress bars, step-by-step instructions, and manual completion triggers.

## Consequences

### Positive
- **High Trust & Explainability**: Operators understand exactly why a hypothesis was generated, backed by observed telemetry facts and topological graph paths.
- **False-Positive Elimination**: Counter-evidence scoring ensures that healthy components are suppressed from ranking #1.
- **Operational Safety**: Eliminates risks of unauthorized automated mutations while providing structured, standardized runbook execution.
- **Audit Compliance**: Full historical lineage from alert ingestion, graph analysis, hypothesis evaluation, human confirmation, to runbook step completion.

### Trade-offs & Mitigations
- *Trade-off*: SREs must manually execute runbook commands rather than clicking an "auto-remediate" button.
  *Mitigation*: This deliberate design decision guarantees tenant safety, eliminates unintended blast radius, and complies with enterprise compliance standards.
